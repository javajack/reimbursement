Every number here is a commitment an implementing agent can test against, not an aspiration: a first load under 5 seconds on a Galaxy A24-class phone, p95 reads in 200 ms, OCR P50 under 5 seconds, 99.5% availability stated honestly for a 2-person team, and a cost envelope that holds the ₹1.0-2.5 per-submission COGS canon. Derivations show their arithmetic; soft figures carry confidence pills. The machine these budgets govern is in [Architecture](/spec/architecture/); the alert thresholds that page a human live in [Ops runbooks](/phase-1/ops-runbooks/).

## Performance budgets

The budget basis is the Performance Inequality Gap analysis (Alex Russell, 2024 and 2026 editions; India is in its market set): P75 budgets of roughly 150 KiB markup/CSS plus 300-350 KiB of gzipped JavaScript for a first load under 5 seconds, with the 2026 baseline device named as a Samsung Galaxy A24 4G-class phone, and JavaScript costing about 3x per byte versus HTML/CSS <span class="pill pill--high">High</span> (primary docs).

| Surface | Budget | Basis |
| --- | --- | --- |
| PWA entry (capture + submit), cold first load | 150 KiB HTML/CSS/fonts + 350 KiB JS, both gzipped; interactive in under 5 s at P75 | Performance Inequality Gap, Galaxy A24-class over 4G |
| PWA repeat visit (service worker warm) | App shell from cache; interactive in under 2 s | Our derivation |
| Console routes (approver, finance, admin) | 500 KiB JS gz ceiling per route | Our derivation; desktop-biased but same discipline |
| `frame_analysis` coaching feedback | Under 100 ms per frame; never worse than 1 s | THESIS instant-feel regime |
| `compress` output | ~2048 px long edge JPEG, quality ~0.8, 200-500 KB per page | Canonical capture pipeline |
| Shutter to saved-in-outbox (`queue_upload`) | Under 1 s, network excluded | Our derivation; trust on dead networks |

The route-level code-splitting rule: the capture route lazy-loads any computer-vision module, always. OpenCV.js is 7.6-8.4 MB stock and 2-4 MB trimmed; no CV bytes ever ship in the entry bundle, the slim build loads only behind runtime feature detection on `navigator.deviceMemory >= 4` devices, and the file-input capture ladder must be fully functional before any CV code arrives. CI enforces the budget: the build fails when the entry chunk exceeds it.

:::danger[Product invariant]
The capture screen works with zero optional bytes loaded. Enhanced viewfinder, edge overlay, and any WASM are progressive enhancement on top of the universal `intake` path; a Galaxy A24 on a flaky 4G cell is the design center, not the worst case. See [Camera capture](/phase-1/capture/camera/).
:::

## API latency and processing targets

Server-side targets, p95 measured at the load balancer in steady state, single region (ap-south-1).

| Endpoint class | Target | Notes |
| --- | --- | --- |
| Reads (GET, cursor-paginated lists, balances) | p95 200 ms | Inbox, claim lists, CreditEntry balance |
| Writes (POST/PATCH: submit, approve, configure) | p95 400 ms | Includes the credit-consumption transaction and chain snapshot |
| Receipt presign issuance | p95 150 ms | Hot path of capture; image bytes never transit the API |
| File generation (payout files, exports) | p95 2 s | Larger jobs go async with a notification on completion |
| OCR extraction (async, server `extract`) | P50 under 5 s; P95 under 60 s | Formal SLO; the P95 warning fires pre-breach at 30 s; P50 over 8 s pages as a sustained breach |
| Outbound webhooks | p95 under 60 s to first 2xx | HMAC-SHA256 signed (`X-Kharcha-Signature`); backoff retries to 24 h, then a visible dead-letter |

The over-10-seconds rule is UX law, not just an SLO: past 10 seconds the Scanning chip switches to determinate progress plus a "we'll notify you" promise, and the employee can navigate away or enter line items manually (Nielsen-derived latency regimes, carried in THESIS). The form never blocks on OCR. Vendor latency claims in this space (Klippa 0.5-4 s, Fyle "seconds") are marketing <span class="pill pill--med">Medium</span>; our P50 target matches them without trusting them.

## Availability: 99.5%, honestly

The MVP target is 99.5% monthly availability on the API and Console: 3.6 hours of allowed downtime per 30-day month (720 h × 0.005, our arithmetic). For a 2-person team with no follow-the-sun rotation, promising 99.9% (43 minutes a month) would be theatre; 99.5% is achievable with managed Postgres across AZs, stateless API replicas, and the degradation ladder below. Planned maintenance runs Sunday 02:00-05:00 IST, at most twice a month, announced 72 hours ahead on the status page, and counts inside the budget: no exclusion-clause arithmetic.

Error budget practice-lite: if more than half the 3.6-hour budget burns in a month, the next cycle ships reliability work before features. The Monday ops review tracks it; no formal SRE ceremony.

Server availability is necessary, not sufficient: the best Indian mobile network's Consistent Quality score is 66.5% (Opensignal, Oct 2024) <span class="pill pill--med">Medium</span>, meaning roughly a third of demanding tests in the image-upload class miss thresholds. The client therefore carries its own availability mechanism, the IndexedDB outbox, and capture never requires the server to be reachable.

### Degradation ladder

| Failure | Blast radius | Behavior while degraded |
| --- | --- | --- |
| OCR provider down | Extraction only | Capture, upload, manual entry, approvals, payouts all continue; receipts park in `queued`; in-app banner per runbook 1 |
| Object storage degraded | New uploads | Client outbox holds blobs; claims whose receipts already uploaded proceed normally |
| WhatsApp BSP down | Nudges | Drop to email; WhatsApp is never the only channel (architecture invariant) |
| Email provider down | Notifications | In-app plus WhatsApp; digests resume on recovery |
| Payment gateway down | Top-ups | Packs cannot be bought; ops grants via ledger `adjustment` against a verified payment (runbook 4) |
| PostgreSQL down | Everything server-side | The one true single point of failure: full outage; PWA capture to outbox still works offline |

:::danger[The queue is the design]
`Receipt.status = queued` absorbs two triggers (credits exhausted, or processing unavailable); `Claim.status = awaiting_credits` has exactly one (company balance 0 at submit). Together they form the application-layer queue the soft paywall of [Credits and metering](/phase-1/credits-and-metering/) defines; top-up or recovery drains it FIFO through the same code path. Nothing an employee captures is ever lost, in any failure mode, including the server being entirely down.
:::

## Observability

Structured JSON logs, one event per line, with `request_id` and `company_id` mandatory on every authenticated line. The request id is generated at the edge, propagated as `X-Request-Id`, and echoed in RFC 7807 problem bodies so a support ticket maps to a trace in one lookup (see [API](/spec/api/)).

```json
{
  "ts": "2026-06-10T08:32:11.412Z",
  "level": "info",
  "request_id": "req_01J9XW8G2K",
  "company_id": "co_01HZX4M9QK",
  "user_id": "usr_01HZY2T8RD",
  "module": "capture",
  "event": "extract.completed",
  "receipt_id": "rcp_01J9XWAB3F",
  "duration_ms": 4180,
  "outcome": "extracted"
}
```

Logging rules: never log image bytes, raw OCR text, beneficiary account numbers, or webhook secrets; `amount_paise` and entity ids are fine. Logs retain 30 days searchable (errors 90 days). AuditEvent is product data, not telemetry: append-only, 8-FY retention (Companies Act, the binding longest), and never conflated with logs.

Metrics are the ten numbers on the monitoring page in [Ops runbooks](/phase-1/ops-runbooks/); a metric that cannot trigger a runbook does not exist. Module ownership: capture owns capture success rate and the stage funnel; extraction owns OCR P50/P95, confidence distribution, and `extraction_failed` rate; credits owns `awaiting_credits` depth, burn anomalies, and payment-webhook lag; approvals owns SLA breaches; payouts owns instruction failure rate.

Telemetry events (client and server) are named for the canonical capture stage names: `intake`, `frame_analysis`, `capture`, `quality_gate`, `crop_correct`, `review`, `compress`, `queue_upload`, `upload`, `extract`, `review_items`. The full event taxonomy with payload schemas lives in [Capture pipeline](/spec/capture-pipeline/). Traces are OpenTelemetry spans: head-sample 10% of requests, always sample errors and any span over 1 s (our derivation; tune after baselines).

## Rate limits

All limits are our derivation, set as starting points and tuned after 4-6 weeks of baselines. Enforcement returns 429 as `application/problem+json` with `Retry-After`, plus `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` headers. `Idempotency-Key` on POSTs makes client retries safe by contract.

| Principal | Sustained limit | Burst | Notes |
| --- | --- | --- | --- |
| Unauthenticated (login, magic link, OTP) | 10/min per IP; 5/hour per identifier | 20 | Brute-force guard; escalates to lockout |
| User session (JWT) | 120 req/min per user | 40 in 10 s | Sized for Scanning-chip polling plus normal use |
| Company aggregate | 1,200 req/min per company | 2,000 | Protects tenant neighbours under RLS |
| API key (integration) | 300 req/min per key | 600 | Configurable per key; scoped keys only |
| Receipt presign issuance | 60/hour per user | 20 in 5 min | Free pre-submission scans already capped at `max(20, 3 × remaining credits)` per company per month |
| File generation | 12/hour per company, 3 concurrent | n/a | Payout files and exports; queue beyond that |
| Webhook test fires | 10/hour per WebhookEndpoint | n/a | Console-triggered |

## Capacity model

Sizing assumptions, stated so they can be wrong in public:

| Assumption | Value | Provenance |
| --- | --- | --- |
| Active companies | 1,000 | Planning scale; matches the architecture scaling story |
| Employees per company | 40 | Our planning assumption, deliberately near the SMB end of the 20-to-500-employee ICP range (most customers will be small) |
| Submissions per employee per month | 4 | Upper half of the 2-6 unbenchmarked estimate <span class="pill pill--low">Low</span>; validate with design partners |
| Receipt images per claim | 2.5 | Our assumption, inside the 5-image fair-use boundary |

Derived load, all arithmetic ours:

- Claims: 1,000 × 40 × 4 = 160,000 per month, about 7,300 per working day (22 working days).
- OCR calls: 160,000 × 2.5 = 400,000 extraction pages per month, plus free pre-submission scans bounded by the fair-use cap above; budget ~15% overhead for retries.
- Queue throughput: 400,000 ÷ 22 ÷ 600 working minutes ≈ 30 `extract` jobs per minute average; design for 100/min peak (about 3x, month-end clustering). pg-boss absorbs this trivially; the first genuine split remains the `extract` consumer, as argued in [Architecture](/spec/architecture/).
- Storage: 400,000 pages × 200-500 KB = 80-200 GB/month of originals; corrected copies roughly double bytes to 160-400 GB/month, so 2-5 TB/year cumulative under 8-FY retention, with lifecycle rules tiering cold objects.
- Database growth: ~25 rows per claim (Claim, LineItems, Receipts, ApprovalSteps, CreditEntry, AuditEvents, Notifications) ≈ 4M rows and roughly 4-8 GB per month including indexes; AuditEvent input snapshots dominate row size.

The architecture page modelled a flatter 100 submissions per company per month (about 4,500 claims per working day on the same 22-day basis; its quoted 3,300/day is calendar-day); this page sizes the heavier 160-per-company case at about 7,300. Both fit the same boring hardware story with headroom.

## The monthly cost envelope

Unit anchors: OCR ₹0.2-0.85 per page (LLM-vision pipeline ₹0.2-0.8 our derivation; Document AI Expense Parser ≈ ₹0.85/page at ₹85/USD, vendor <span class="pill pill--high">High</span> for the price itself); compute plus Postgres ₹0.2-0.5 per submission (THESIS canon); storage under ₹0.05 per submission; WhatsApp utility template ₹0.115-0.145 per message plus 18% GST (Meta/BSP, vendor <span class="pill pill--med">Medium</span>, re-verify at build time); transactional email ≈ ₹0.13 per email at the Postmark anchor ($15 per 10k, vendor; a deliverability-premium ceiling). Behavioral assumptions: 1 WhatsApp nudge and 2 digest-batched emails per claim, every company at the full 160-submission profile (overstates free-tier pilots, so this is an upper-bound envelope).

| Cost line | 100 companies (16k subs/mo) | 1,000 companies (160k subs/mo) | 10,000 companies (1.6M subs/mo) |
| --- | --- | --- | --- |
| OCR (2.5 pages × ₹0.2-0.85) | ₹8,000-34,000 | ₹0.8-3.4 lakh | ₹8-34 lakh |
| Compute + Postgres (₹0.2-0.5/sub) | ₹3,200-8,000, floor-dominated | ₹32,000-80,000 | ₹3.2-8 lakh |
| S3 (receipts, files, exports) | under ₹800 | under ₹8,000 | under ₹80,000 |
| WhatsApp nudges (₹0.145 ex-GST) | ≈ ₹2,300 | ≈ ₹23,000 | ≈ ₹2.3 lakh |
| Email (₹0.13, Postmark ceiling) | ≈ ₹4,200 | ≈ ₹42,000 | ≈ ₹3.3 lakh with tier decline |
| Total per month | ≈ ₹19,000-49,000 | ≈ ₹1.9-4.9 lakh | ≈ ₹17-48 lakh |
| Per submission | ₹1.2-3.1 | ₹1.2-3.1 | ₹1.1-3.0 |

<p class="source-note">Our derivation throughout, from THESIS unit costs and the vendor anchors named above. Linear by construction: volume discounts (OCR tier pricing, email tiers) are noted but not modelled, so large-scale totals skew high.</p>

:::caution[Two honest wrinkles]
First, at 2.5 receipts per claim the Document-AI-everywhere worst case is ₹2.13 of OCR alone, pushing the all-in past the ₹2.5 canon top; that is exactly why `OCRProvider` is provider-agnostic and LLM-vision (₹0.2-0.8/page) is the default. The ₹1.0-2.5 COGS canon holds on that midline. Second, below roughly 300 paying companies the fixed floor (managed Postgres, two always-on containers, status page) dominates the variable arithmetic; this envelope is a variable-cost model, not a startup budget.
:::

Against realised pack prices of ₹5.00-9.98 per credit, the margin canon holds: 67-75% gross at ₹5, 80-90% at ₹8-10, and the ₹4 enterprise floor preserves headroom even at the ₹3.1 worst-case all-in. The revenue side of this arithmetic lives in [Unit economics](/strategy/unit-economics/).

## Browser and device commitments

The test matrix, restated as commitments. Android holds 93.2% of Indian mobile and iOS 6.7% (StatCounter, May 2026) <span class="pill pill--high">High</span>; Android 11 and later sum to ~90% of the Android base, so evergreen Chrome is the norm.

| Tier | Environment | Commitment |
| --- | --- | --- |
| 1 | Android 11+, evergreen Chrome, Galaxy A24-class baseline | Full PWA: WebAPK install, Web Share Target, web push, offline outbox; enhanced viewfinder where `deviceMemory >= 4` |
| 1 | WhatsApp and Gmail in-app browsers (Android) | Capture and submit work end to end on the file-input ladder; no install, no push, no excuses |
| 1 | iOS Safari, current and previous major version | File-input capture (default in standalone per WebKit bug 252465), A2HS coaching only, notifications via WhatsApp/email; outbox replays on app-open (no Background Sync on Safari) |
| 1 | Desktop Chrome and Edge, latest two versions | Console fully supported |
| 2 | Desktop Firefox and Safari, latest two versions | Console supported; capture path functional, not optimised |
| 2 | Android 9-10 or 2-3 GB RAM devices | File-input path only; functional, best-effort polish |

Done means: every release is smoke-tested on a physical Galaxy A24-class device; the CI bundle gate is green; a bill can be captured and submitted inside the WhatsApp in-app browser; iOS standalone capture uses the file input by default; and the ten monitoring metrics are emitting before any feature flag flips on.
