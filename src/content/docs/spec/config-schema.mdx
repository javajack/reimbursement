Every tenant decision in Phase 1 lives in one versioned JSON document per company: eight domains under one schema, validated atomically on save, snapshotted into every Claim. [The configuration model](/phase-1/onboarding/configuration-model/) explains how the model behaves: defaults, binding moments, mid-flight semantics. This page is its normative companion: the exact schema an implementing agent codes against, every default and its reason, the save-time error codes, and a complete worked example.

## Envelope and access

The document is identified by the constant `kharcha.config/v1`. The Console reads and writes it through the standard API conventions: `GET /api/v1/company-config` returns the current document; `PUT /api/v1/company-config` replaces it whole (the Console edits one domain at a time but always submits the full document); `POST /api/v1/company-config/validate` dry-runs the full validation gate without saving; `POST /api/v1/company-config/simulate-claim` renders the chain a hypothetical claim (employee, amount, category) would take, plus which rule fired, the simulate-before-activate tester; `GET /api/v1/company-config/versions` lists the version history described under [versioning](#versioning-and-migration). This surface is the binding config API; the [API page](/spec/api/) catalogs the same five endpoints. Writes carry the client's last-seen `version`; a mismatch returns `409` with code `CFG_VERSION_STALE`. Exports add an `exported_at` timestamp; imports run the identical validation plus a diff preview before activation.

One deliberate absence: people. The model page lists nine domains; the ninth (Users, Memberships, manager edges, Departments, CostCenters, Grades) is directory data mastered in its own tables in the [data model](/spec/data-model/). Config references the directory by stable code or id and never embeds it; referential checks below enforce that those references resolve.

Normative notes an agent must honor:

- Unknown keys fail validation (`CFG_SCHEMA_INVALID`); they are never silently dropped. Forward compatibility is handled by migrations, not lax parsing.
- All money is integer `amount_paise` (or `_paise` suffixed); effective windows are ISO 8601 date-only; ids are prefixed ULIDs per the API conventions, with `br_` (branch) and `cfgv_` (config version) derived here.
- `approval.rules` items are full Rule objects per the [rule schema](/spec/rule-schema/), constrained to `action: route` and `scope: claim`. Claim-scope conditions see aggregates: `amount_paise` is the claimed total, `line_categories` is the set of category ids across line items. Lowest `priority` number fires first; the first matching rule builds the chain. The `params.chain` and `params.add_steps` arrays carry `"maxItems": 5`; a longer chain fails the save with `CFG_CHAIN_TOO_LONG`. Embedded rules also run the rule schema's own validation in the same gate, and violations reject with that page's codes rather than being coerced (for example, `action: block` with soft hardness fails with `RULE_BLOCK_NOT_HARD`).
- `doa_grid` overlays the resolved chain: the chain must end at a slot whose `limit_paise` covers `claimed_amount_paise`; when it tops out, the engine appends the next sufficient slot. Mechanics live in the [approval engine](/phase-1/web/approval-engine/).
- `file_format` values are keys into the bank-file registry in [bank files](/reference/bank-files/), shipped and versioned by us.
- `grade_code` references the Grade directory entity's stable snake_case code, not a display label.
- An event absent from `notifications.events` resolves to `["email"]`; an empty array means silenced for that event.

:::caution[No secrets in the document]
Full bank account numbers never enter the config document. They are captured in the Console, stored encrypted in the `bank_accounts` table, and surface here only as `account_last4`. Exports are therefore safe to attach to support tickets; imports can update account metadata but can never mint a usable account without re-entry of the number in the Console.
:::

## Resolution order

Exactly one rule, evaluated at snapshot time: branch value if explicitly set, else company value, else system default. The claim snapshot records each resolved value and its source layer. Branch overrides are a closed allowlist, not a general mechanism:

| Config path | Branch override | Mechanism |
| --- | --- | --- |
| `domains.approval` | Yes | Whole-object swap via `branches[].overrides.approval` |
| `domains.payouts.default_bank_account_id` | Yes | `branches[].overrides.payouts`; enables per-branch payout files |
| Branch `gstin` | Not an override | Branch-owned; GST registration is per state |
| `categories`, `policy_tables`, `locale`, `notifications` | No | Company-wide; vary by branch through rule conditions instead |
| `credits` | Never | The meter is submissions per Company; branches share one balance |

## Validation on save

The gate runs four passes. Schema validation short-circuits (a malformed document cannot be analyzed); the semantic passes (referential, graph, temporal) all run and return the complete error list, because admins fix configuration in batches. Errors return `422` as RFC 7807 `application/problem+json` with an `errors[]` array; warnings save successfully and return in a `warnings[]` array. Graph checks also run on user saves (a manager-pointer edit can break a chain without touching config).

| Code | Catches | Severity |
| --- | --- | --- |
| `CFG_VERSION_STALE` | Write carries a `version` older than the server's (returns `409`) | error |
| `CFG_SCHEMA_INVALID` | Type, enum, pattern, bounds, or unknown-key violation anywhere | error |
| `AP_FALLBACK_MISSING` | `approval.rules` has no `rule_fallback` entry | error |
| `AP_FALLBACK_IMMUTABLE` | `rule_fallback` condition, priority, or enabled flag modified | error |
| `AP_CYCLE` | Resolved approver graph contains a cycle | error |
| `AP_ORPHAN_SLOT` | A chain slot resolves to no active user | error |
| `AP_PRIORITY_DUPLICATE` | Two enabled routing rules share a priority number | error |
| `AP_SELF_APPROVAL_PATH` | A manager pointer makes a user their own approver | error |
| `CFG_CHAIN_TOO_LONG` | A rule's `chain` or `add_steps` array exceeds 5 slots | error |
| `REF_UNKNOWN_GRADE` | `per_diem_matrix` row references a grade code not in the directory | error |
| `REF_DEACTIVATED_USER` | A rule, DoA row, or override references an unknown or deactivated user | error |
| `REF_UNKNOWN_CATEGORY` | A rule condition references a category id not in `categories.items` | error |
| `REF_UNKNOWN_BANK_ACCOUNT` | A `default_bank_account_id` not present in `payouts.bank_accounts` | error |
| `PT_DATE_OVERLAP` | Two versions of one policy table have overlapping effective windows | error |
| `PT_GAP` | No policy-table version covers today, or windows leave a gap | warning |
| `CAT_NONE_ACTIVE` | Zero active categories (violates the three hard requirements) | error |
| `CAT_DUPLICATE_ID` | Two categories share an id | error |
| `PO_CALENDAR_INCOMPLETE` | `weekly`/`fortnightly` without `weekday`, or `monthly` without `day_of_month` | error |
| `CR_CAP_TOO_LOW` | Auto-top-up enabled with `monthly_cap_paise` below one configured pack's ex-GST price | error |
| `LC_DEFAULT_NOT_LISTED` | `locale.default` missing from `locale.languages` | error |

```json
{
  "type": "https://errors.kharcha.in/config-validation",
  "title": "Configuration failed validation",
  "status": 422,
  "errors": [
    {
      "code": "AP_ORPHAN_SLOT",
      "path": "/domains/approval/rules/2/params/chain/0",
      "message": "department_head resolves to no active user for the Sales department."
    },
    {
      "code": "PT_DATE_OVERLAP",
      "path": "/domains/policy_tables/per_diem_matrix/1",
      "message": "Window starting 2026-04-01 overlaps the version effective 2026-01-01 to 2026-06-30."
    }
  ]
}
```

:::note[The fallback rule is a constant]
`rule_fallback` is the one rule id that is not a ULID. It is system-seeded, always-matching (condition `all: []`), pinned at maximum priority, undeletable, and never disabled; only its route target may be retargeted. It fires when no rule matches, routing the claim to the submitter's manager (the seeded chain is `["manager"]`). When even that resolves to nobody (no manager on record), the resolver floor, not the rule's params, parks the claim in the admin queue flagged `rule_gap`; the [approval engine](/phase-1/web/approval-engine/) owns that floor. This is why a Claim is never blocked at submission for routing reasons, the invariant the model page sets against Zoho's hard block.
:::

## Defaults

Every key ships working. The wizard writes a handful; everything else is a system default an admin may never touch.

| Key | Default | Why |
| --- | --- | --- |
| `org.fiscal_year_start` | `"04-01"` | India's statutory Apr-Mar FY; anchors reporting periods and rate versioning |
| `org.currency` | `"INR"` | Phase 1 is India-only; a constant, not a choice |
| `org.gstin` | `null` | Skippable at signup; improves ITC tagging, never gates a claim |
| `org.branches` | `[]` | Implicit head office; branches enter at multi-GSTIN reality, capped at 200 |
| `categories.items` | 10-category India set, all active | First claim must need zero category setup |
| `categories.items[].gst_hint` | Statutory mapping (Meals `itc_blocked_17_5`, Travel `itc_eligible`) | Sec 17(5) informational tagging for finance; admins override the hint, not the law |
| `categories.items[].non_reimbursable` | `false` | Recording-only categories are an explicit opt-in |
| `policy_tables.per_diem_matrix` | `[]` | No statutory per-diem amounts exist; PER_DIEM_CAP stays inert until a table exists |
| `policy_tables.mileage_rates` | `[]` | India has no statutory per-km rate; rates are a company decision |
| `approval.template` | Wizard pick; `under_50` if created via API | Manager-only is the safest seed |
| `approval.rules` | Template rules plus `rule_fallback` | Claims must always route |
| `approval.self_approval` | `"skip_up"` | There is no allow mode; only the substitution strategy is configurable |
| `approval.doa_grid` | `[]` | The Concur-style grid is an option for DoA-minded finance teams, not a requirement |
| `credits.alert_thresholds` | `[50, 80, 95, 100]` | THESIS canon: an alert fires once per cycle at each threshold, plus the burn-rate forecast |
| `credits.auto_topup.enabled` | `false` | Spending money is always an explicit opt-in |
| `credits.auto_topup.threshold` | `10` | Early enough to drain the queue before exhaustion (our derivation) |
| `credits.auto_topup.monthly_cap_paise` | `null`, required when enabled | A hard cap is the difference between auto-top-up and bill shock |
| `payouts.bank_accounts` | `[]` | Required before the first payout run, never the first claim |
| `payouts.default_rail` | `"neft"` | Uncapped and batch-native; IMPS/UPI per-transaction caps make them per-instruction choices |
| `payouts.payout_calendar.frequency` | `"manual"` | No calendar should fire before a bank account exists |
| `notifications.events.*` | `["email"]` for all eight events | Email is the only universal day-one channel; `web_push` after PWA install; `in_app` is always available; `native_push` arrives later with the future native apps |
| `notifications.quiet_hours` | `21:00` to `08:00`, `Asia/Kolkata` | Approver nudges respect IST nights (approver-UX canon) |
| `locale.languages` | `["en-IN", "hi-IN"]` | Hindi plus English from day one is the vernacular stance |
| `locale.default` | `"en-IN"` | Tenants flip the default in one edit; the worked example does |

<p class="source-note">Defaults are our derivation over THESIS-V2 contracts and the onboarding canon; none are vendor claims.</p>

## Worked example: a 120-person field-sales company

Saral Krishi Equipments sells farm implements through 120 field staff across Maharashtra and Madhya Pradesh: two GST registrations (Pune head office, Indore), three grades, the 50-250 wizard template customized with a fuel-specific rule, payout files cut every Tuesday, Hindi as the default display language. At 4 submissions per employee per month (THESIS planning estimate, unbenchmarked; validate with design partners) <span class="pill pill--med">Medium</span> the company burns about 480 credits monthly, so a Growth pack of 1,000 credits lasts roughly two months and the auto-top-up cap of ₹13,998 (two Growth packs, ex-GST) bounds worst-case spend. ## Versioning and migration

Every successful save appends a row to `config_versions`; nothing updates in place. The row stores the full post-save document plus an RFC 6902 diff against the previous version, which is what the Console renders as who-changed-what history.

```sql
CREATE TABLE config_versions (
  id                   text PRIMARY KEY,          -- cfgv_ ULID
  company_id           text NOT NULL REFERENCES companies(id),
  version              integer NOT NULL,          -- monotonic per company
  schema               text NOT NULL DEFAULT 'kharcha.config/v1',
  document             jsonb NOT NULL,            -- full document, post-save
  diff                 jsonb NOT NULL,            -- RFC 6902 patch vs previous version
  domains_touched      text[] NOT NULL,
  actor_membership_id  text REFERENCES memberships(id),  -- NULL for system migrations
  created_at           timestamptz NOT NULL DEFAULT now(),
  UNIQUE (company_id, version)
);
```

Three semantics bind this table to the rest of the system:

1. **In-flight snapshot reference.** At submission, a Claim freezes its resolved configuration (chain, rates, category metadata, source layers) into its snapshot and records the company `version` plus the per-domain version vector as provenance. Later saves never touch it; the explicit re-route action on the model page is the only path, and it writes AuditEvents linking both matrix versions.
2. **Who-changed-what.** Every save also emits an AuditEvent (actor, role at the time, before and after); `config_versions.diff` is the canonical payload the audit UI and support tooling read. `domains_touched` makes "show me every approval change this quarter" an index scan.
3. **Schema migration.** A move to `kharcha.config/v2` ships as a forward-only deploy-time migration that rewrites every tenant document and appends a version row with `actor_membership_id NULL`. History rows are never edited; old rows keep their original `schema` value and remain renderable.

:::danger[Snapshots embed values, not pointers]
Claim snapshots store resolved values, never references into `config_versions`. A schema migration, a branch deletion, or a policy rewrite must never change what an already-submitted Claim means. The version numbers in the snapshot are provenance for auditors, not a dependency for evaluation. Tables and constraints live in the [data model](/spec/data-model/).
:::

## What is not configuration

The document's edges matter as much as its contents. Four things deliberately live outside it:

| Lives elsewhere | Examples | Why not config |
| --- | --- | --- |
| Statutory tables, shipped by us, FY-versioned | GSTIN format and checksum, state-code list, Sec 17(5) blocked-ITC mapping behind `gst_hint` defaults and ITC_ELIGIBLE | Tenants opt in and out of rules; they never edit the law. We ship updates with releases, versioned by fiscal year |
| System limits | 200 branches; 5 receipt images per claim then +1 credit per extra 5; pre-submission OCR fair-use of `max(20, 3 × remaining credits)` scans/month; pagination limit 100; 20 Free submissions/month | Guardrails and fair-use are product economics, not tenant preferences |
| Plans and packs | The `Free`, `Starter`, `Growth`, `Scale` plans; the Top-up through Enterprise prepaid packs, their prices and validity | Pricing is ours; the config only records auto-top-up intent. Numbers live in the pricing ladder |
| Directory and ledger data | Users, Memberships, Grades, Departments; the CreditEntry ledger; BeneficiaryAccounts | Mastered in their own tables; config references them and validation keeps the references honest |

## Done means

- The published schema file validates the worked example above byte-for-byte, and rejects each error-code scenario in the validation table with that exact code and a JSON Pointer path.
- A tenant created via API with an empty body beyond `org.legal_name` boots into the full defaults column and can run claim through approval without touching settings.
- `PUT` with a stale `version` returns `409 CFG_VERSION_STALE`; concurrent admin edits can never silently overwrite each other.
- Every save produces a `config_versions` row whose `diff` replays cleanly from the prior document, and an AuditEvent pointing at it.
- Deleting `rule_fallback`, disabling it, or editing its condition is impossible through any API path, not just hidden in the UI.
