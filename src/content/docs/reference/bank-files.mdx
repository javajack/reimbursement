Bank bulk-payment formats are not a stable spec you can hard-code once. They are bank-specific, channel-specific, versioned, and often published only inside the corporate net-banking portal. The fields below are indicative, assembled from secondary and summary sources; the ICICI v3.3 PDF could not be machine-parsed and the Kotak field doc was not independently fetched. Treat this page as build orientation, not a contract. Confirm every format against the bank's primary file-format document or the customer's relationship manager before you write a serializer.

This matters because file hand-off is the Phase 1 disbursement architecture: finance builds a [PayoutBatch](/phase-1/payouts/) of approved claims, Kharcha exports a bulk file in the customer's bank format, and the customer uploads and authorizes it in their own corporate net banking. Money flows from the customer's own current account; funds never touch an account we own. [Money movement](/compliance/money-movement/) explains why that boundary is the whole regulatory game.

:::caution[Indicative, not authoritative]
Field order, fixed-width positions, encryption requirements, header and footer rows, and per-file caps differ by bank and channel and change between versions. Verify against the bank's own spec per integration. Confidence on the per-bank detail below is <span class="pill pill--med">Medium</span> and lower for HDFC, SBI, and Kotak.
:::

## Common fields across bank bulk files

Despite format divergence, the payload converges on a small set of fields. The internal record is the PayoutInstruction (`pin_` prefix; see the [data model](/spec/data-model/)); a per-bank serializer maps it to that bank's columns or fixed-width positions. Money is `amount_paise` internally; the serializer formats it as a rupee-decimal string at the last moment.

| Field | Purpose | Notes |
| --- | --- | --- |
| Beneficiary name | Payee display name | Banks may match against beneficiary master; name mismatch can reject |
| Account number | Credit account | From the verified BeneficiaryAccount; validate length per bank before emit |
| IFSC | Routing to branch | 11 characters; drives NEFT/RTGS/IMPS routing |
| Amount | Payout value (₹) | Serialized from `amount_paise`; drives rail selection by threshold |
| Payment mode | NEFT / RTGS / IMPS / internal | Some banks auto-segregate by amount and IFSC |
| Narration / remarks | Statement reference | Carries the Kharcha claim reference; the reconciliation hook |
| Email / mobile | Beneficiary alert | Optional; used for credit advice |
| Source / debit account | Which current account to debit | A company BankAccount record; one file per source account |

Beneficiary details come only from a verification-gated BeneficiaryAccount, never free-typed at batch time. Emit one file per source BankAccount: a company paying travel reimbursements from one current account and field allowances from another gets two files per run.

### Narration convention

The narration is the single thread that survives the round trip through the bank. Phase 1 convention: `KHARCHA-REIMB-` plus the claim reference. The canonical claim id is a prefixed ULID, for example `clm_01JC4QH7VXK8ZT2M9R3EW5YA`; the serializer sanitizes it per bank rules, stripping the underscore where only alphanumerics are allowed and truncating the ULID where the field is length-capped (caps vary by bank, roughly 20 to 40 characters in the formats reviewed; verify per bank), yielding narrations like `KHARCHA-REIMB-clm01JC4QH7`. When even the truncated claim reference does not fit, the serializer falls back to a short batch reference (batch sequence number plus row index, for example `B0421-017`); the PayoutBatch record holds the mapping from that reference back to the `pin_` id. In Phase 2, vendor payouts will carry a `KHARCHA-VND-` prefix; that is documented with the rest of the vendor flow in [Phase 2 payouts and AP](/phase-2/payouts-and-ap/), not here.

## Per-bank notes

| Bank / channel | Format | Modes | Notable detail |
| --- | --- | --- | --- |
| ICICI CIB | Fixed-width / converter XLS (file format v3.3) | NEFT, RTGS, Bulk IMPS, cheque, DD, direct credit | Separate salary, vendor, dealer, and external file types; the external file adds source and destination branch and account IDs, currency, account type, remarks; encrypted upload |
| HDFC ENet / CBX (H2H) | Excel / text template | NEFT, RTGS, IMPS, A2A | Columns: Beneficiary Name, Account No., IFSC, Amount, Remarks; per-file cap ~1,000 txns / ₹10 crore (secondary upload manual; confirm against current ENet spec) |
| Axis PayPro / CIB | CSV / XLS / TXT (generic or customer format) | RTGS, NEFT, IMPS, internal, DD, cheque | Single-file upload with auto-segregation by payment identifier; beneficiary-master validation; encrypted files; returns UTR-level status |
| SBI Corporate (CINB) | Single-debit-multiple-credit file | Intra-bank, NEFT, RTGS | Symmetric-key or PKI file encryption; other-bank consolidated limit up to ~₹50 lakh/txn, ~₹2 crore/day (portal-sourced, verify) |
| Kotak Corporate Net Banking / H2H | CSV / fixed-width / XML (verify) | NEFT, RTGS, IMPS | Commonly documented bulk fields (beneficiary name, account no., IFSC, amount, mode, narration) are unverified for Kotak; field-format doc not independently confirmed |

<p class="source-note">Source: bank cash-management pages and bulk-upload summaries (vendor / primary, medium confidence; HDFC, SBI, Kotak lower). ICICI v3.3 PDF not machine-parsed; Kotak fields unverified.</p>

:::note[Encryption is part of the format]
SBI requires symmetric-key or PKI file encryption; ICICI and Axis use encrypted upload. The bytes you emit are only half the integration. Plan for the bank's key exchange, header and footer conventions, and checksum rows alongside the field mapping.
:::

## Rails and limits

Rail selection is driven by amount and urgency. NEFT is the cheapest and uncapped batch rail, RTGS is the high-value rail, IMPS and UPI are the instant rails with hard ceilings. Bank-imposed sub-limits can sit below these NPCI/RBI ceilings, so re-verify at build time.

| Rail | Minimum | Maximum | Timing | Phase 1 use |
| --- | --- | --- | --- | --- |
| NEFT | ₹1 (no floor) | No maximum | 24x7 since 16 Dec 2019, batch | Default for the reimbursement batch; cheapest |
| RTGS | ₹2 lakh | No maximum | 24x7 since 14 Dec 2020 | Rare for employee claims; main rail for Phase 2 vendor payouts |
| IMPS | None | ₹5 lakh per txn | Instant, 24x7 | Instant reimbursement when the employee should not wait |
| UPI | None | ₹1 lakh standard; ₹5 lakh per txn only for named categories; ₹10 lakh/day P2M | Instant | VPA disbursement via the optional payout API, not bank files |

<p class="source-note">Source: ClearTax (NEFT/RTGS/IMPS limits); NPCI circular UPI-OC-185A and DD News (UPI limits). Govt/analyst, high confidence on ceilings; bank sub-limits may be lower.</p>

Online NEFT and RTGS carry no RBI processing charge (banks may levy their own fee). The enhanced ₹5 lakh UPI category limits (insurance, capital markets, education, hospitals, government e-marketplace, IPO) do not apply to reimbursements: plan around the ₹1 lakh UPI and ₹5 lakh IMPS ceilings. Nearly every employee claim sits far below all of these, so NEFT batch is the sane default and IMPS the urgency override.

## Sample employee-reimbursement file

The canonical internal shape before the per-bank serializer runs. Real bank templates rename columns, reorder, or switch to fixed-width; this is what we hold and transform.

```csv
source_account,beneficiary_name,account_number,ifsc,amount,mode,narration,email,mobile
50200012345678,Ramesh Kumar,123456789012,HDFC0001234,4850.00,NEFT,KHARCHA-REIMB-clm01JC4QH7,ramesh@acme.in,9876543210
50200012345678,Sunita Devi,987654321098,ICIC0004567,12300.50,NEFT,KHARCHA-REIMB-clm01JC4RT2,sunita@acme.in,9123456780
50200012345678,Arjun Mehta,556677889900,SBIN0009988,780.00,IMPS,KHARCHA-REIMB-clm01JC4SK9,arjun@acme.in,9001234567
```

Each row is one PayoutInstruction; the amount is the claim's `approved_amount_paise` (which may be below the claimed amount after a `cap` rule fired), serialized to rupees. The narration carries the claim reference, which is what makes return-file reconciliation tractable: the UTR comes back, the narration ties it to the claim, the claim moves `in_payout` to `paid`. Transition guards live in [state machines](/spec/state-machines/).

## Return files and UTR reconciliation

Reconciliation is UTR-centric. Banks return a UTR in status reports and return files; the optional payout-API path delivers the same through webhooks. Ingest both, auto-match to the originating PayoutInstruction, and surface retry or repair for failures in the [finance console](/phase-1/web/finance-console/). This is the operational edge over raw net banking.

| Field | Source | Purpose |
| --- | --- | --- |
| UTR | Bank return file / provider webhook | Unique transaction reference; primary match key |
| Instruction reference | Our system (`pin_` id) | Secondary match key; survives UTR-less states |
| Status | Return file / webhook | <span class="pill pill--allow">Processed</span> / <span class="pill pill--flag">Pending</span> / <span class="pill pill--block">Failed</span> |
| Narration / remarks | Echoed from our file | Carries the claim reference for matching |
| Failure reason | Bank / provider | Drives retry vs repair routing (wrong account vs transient) |
| Processed timestamp | Bank / provider | SLA and ageing on stuck payouts |

Match on UTR first, fall back to instruction reference and narration when the UTR is absent (a failed or pending payout has no UTR yet). After the customer executes the file in net banking, finance marks the batch `executed` (manually confirmed or via return-file upload), individual instructions resolve, and the batch reaches `reconciled`. The full mark-executed flow, including partial failures and re-batching of failed instructions, is specified in [payouts](/phase-1/payouts/).

## File integrity practice

The exported file is a financial instrument the moment it leaves us, so it is treated as immutable evidence, not an editable artifact.

| Practice | Rule |
| --- | --- |
| Hash on export | SHA-256 of every exported file is recorded on the PayoutBatch and logged as an AuditEvent, with actor, timestamp, and instruction count |
| No post-generation edits | Amounts, beneficiaries, and narrations are frozen at export; the UI offers no edit on an `exported` batch |
| Regenerate, never edit | Any change (drop a claim, fix a beneficiary) cancels or supersedes the batch and regenerates a fresh file with a fresh hash; hand-edited files are unsupported and unreconcilable |
| Verify on dispute | If the bank-side total disagrees, the logged hash settles whether the executed file is the one we generated |

:::danger[Funds never touch our account]
File hand-off keeps Kharcha outside RBI Payment Aggregator scope because the customer's own bank moves the money. The moment reimbursement funds pool into an account we control, the model can be re-characterized as a PA (net worth ₹15 crore at application, ₹25 crore by year 3, mandatory escrow) or a PPI. Written legal opinion before go-live. Details in [money movement](/compliance/money-movement/).
:::
