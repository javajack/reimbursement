# VERIFY: For in-browser document scanning: OpenCV.js WASM builds are large (several MB, trimmable); jscanify is a free MIT-licensed library doing edge detection + perspective correction on top of OpenCV.js; Dynamsoft and Scanbot Web SDKs are commercial with annual license fees in the four-to-five-figure USD range; browser-side preprocessing (deskew, binarization, glare handling) measurably improves OCR accuracy.

- **Verdict:** confirmed  (confidence: medium)
- **Corrected / best-supported:** All four sub-claims hold as of June 2026, with precise figures: (1) Default OpenCV.js builds are ~7.6-8.4 MB; custom builds via the opencv_js.config.py whitelist trim to ~2-4 MB typical, ~0.8 MB extreme minimum. (2) jscanify is MIT-licensed (verified on GitHub and npm registry), actively maintained (v1.4.2, Jan 2026, ~10k weekly downloads), and does Canny edge detection + contour finding + perspective correction (plus glare suppression since v1.3.0) on top of OpenCV.js, which must be loaded separately (not bundled). (3) Dynamsoft's document-scanning SDK (Document Normalizer) starts at USD 1,249/year per its own quote page (four figures, scaling up with deployment); Scanbot uses a fixed annual license fee with no published prices — third-party data (SaaSworthy) puts its starting price at ~EUR 20,000/year, i.e. Scanbot's entry point is five figures only, so 'four-to-five-figure' is right as a combined range but four-figure Scanbot deals are not in evidence. (4) Measured OCR gains from preprocessing exist: PreP-OCR (arXiv, May 2025) measured 63.9-70.3% relative character-error-rate reduction vs raw images on 13,831 historical pages; a Nov 2025 benchmark (DKDS) measured ~27.6% relative CER reduction from binarization alone; Bieniecki et al. (IEEE 2007) showed perspective/skew correction is critical for camera-captured docs. Caveats: gains are corpus-dependent, Tesseract already binarizes internally (Otsu) so naive extra binarization can be redundant, no rigorous glare-specific OCR measurement was found, and popular '5-15%' blog figures are unsourced. On alternatives: MediaPipe offers NO web document scanner (Google's document scanner is ML Kit, Android-only per mediapipe issue #5776); ONNX corner-detection models (e.g. DocAligner) run in-browser via onnxruntime-web with WASM/WebGPU (WebGPU now ~82% global support: Chrome/Edge 113+, Safari 26+, Firefox partial), but ONNX/TFLite runtimes carry multi-MB WASM of their own, so they are not automatically lighter than a trimmed OpenCV.js build.

## Reasoning

Each sub-claim was checked against primary sources where possible. (1) OpenCV.js size: official OpenCV docs document custom JS builds; the Lambda IT engineering blog measured the default build at ~7.6 MB and halved it by dropping the DNN module; OpenCV forum threads report 8.4 MB default trimmed to 4.2 MB, and one user reached ~800 KB by stripping unused bindings — 'several MB, trimmable' is accurate. (2) jscanify: GitHub repo and the npm registry JSON both state MIT license; README confirms it is 'powered with opencv.js', does paper detection/highlighting and distortion (perspective) correction, requires OpenCV.js to be loaded separately; registry shows v1.4.2 modified 2026-01-17 and ~10,086 downloads in the last week — free, MIT, active: confirmed. (3) Pricing: Dynamsoft's own ask-for-quote page states 'Prices start at USD 1,249/year' for Document Normalizer (its doc-scan engine; Web TWAIN tiers are email-gated, per-computer); Scanbot's docs confirm a fixed annual license fee model with custom quotes and no public figures; SaaSworthy (third-party) reports Scanbot starting at ~EUR 20,000/year (~USD 22k). The combined 'four-to-five-figure annual' range is therefore supported at both ends, though the Scanbot figure rests on aggregator data the vendor neither publishes nor denies — this is the main reason confidence is medium rather than high. (4) OCR gains: Tesseract's official ImproveQuality docs (qualitative, authoritative) state skew 'severely impacts' OCR quality and internal Otsu binarization is suboptimal on uneven backgrounds; quantitatively, PreP-OCR (arXiv 2505.20429) measured 63.9-70.3% relative CER reduction from a restoration+preprocessing pipeline, DKDS (arXiv 2511.09117) measured ~27.6% relative CER reduction from binarization on degraded documents, and Bieniecki et al. 2007 (IEEE, FineReader 7.0) demonstrated geometric correction is essential for camera-captured documents. So 'measurably improves' is confirmed, with the caveats that magnitudes vary widely by corpus, the often-quoted 5-15% blog numbers are unsourced marketing content, and I found no credible glare-specific OCR measurement (glare handling exists as a feature in jscanify v1.3+ and commercial SDKs, but its isolated OCR impact is unquantified publicly). (5) Alternatives check: MediaPipe has no document-scanner task for web — Google's Document Scanner API is ML Kit, Android-only (confirmed via google-ai-edge/mediapipe issue #5776, Dec 2024, still requesting iOS/web); lightweight deep-learning corner detectors exist in ONNX (DocsaidLab DocAligner) and run via onnxruntime-web (WebGPU EP available; Transformers.js v3 added WebGPU Oct 2024); WebGPU global support is ~82% per caniuse (June 2026). Note the trade-off: onnxruntime-web's own WASM payload is several MB, so the ONNX route mainly buys robustness (ML-based detection) rather than smaller bundles versus a trimmed OpenCV.js.
