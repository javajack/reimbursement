# VERIFY: Mobile getUserMedia honors resolution/aspect constraints only loosely; stretched-bill distortion is a CSS/canvas scaling mismatch vs true videoWidth/videoHeight and is fully fixable in web code; ImageCapture.takePhoto gives full-sensor stills but is Android-Chrome-only (no iOS Safari); iOS Safari supports getUserMedia in standalone PWAs since iOS 13.4; torch/zoom/focus constraints work on Android Chrome but largely not on iOS.

- **Verdict:** partially-confirmed  (confidence: high)
- **Corrected / best-supported:** As of June 2026: (1) CONFIRMED — getUserMedia constraints are requests, not guarantees: bare/ideal values are explicitly non-required and the browser returns the closest supported mode (only exact/min/max are mandatory and can throw OverconstrainedError), so mobile streams routinely differ from the requested resolution/aspect (MDN). (2) CONFIRMED — the delivered frames themselves are undistorted at the stream's intrinsic videoWidth×videoHeight; stretching arises in presentation/capture: object-fit:fill "stretched to fit" when box aspect mismatches (MDN), or a canvas bitmap sized from the layout box instead of videoWidth/videoHeight. Fully fixable in web code via the canonical pattern: request ideal constraints -> wait for metadata and read video.videoWidth/videoHeight -> preview with explicit CSS box + object-fit:cover (crops, never stretches) -> capture with canvas.width=video.videoWidth, canvas.height=video.videoHeight, ctx.drawImage(video,0,0,w,h); for WYSIWYG against a cover-cropped preview use 9-arg drawImage with a source-rect crop matching the box aspect (MDN "Taking still photos" + drawImage). (3) OUTDATED on the Safari half — takePhoto is a true photographic exposure ("highest available photographic camera resolution", Chrome; W3C spec distinguishes it from grabFrame's video-resolution snapshot) and has shipped in Chrome 59+ (Android+desktop, 2017); but WebKit shipped the Image Capture API in Safari 18.4 (iOS 18.4, Mar 31 2025: takePhoto, getPhotoCapabilities, getPhotoSettings) and grabFrame in Safari 26.0 (Sep 2025) — so "iOS Safari no" was true only through iOS 18.3; note caniuse's curated page still lags WebKit's own release notes here, and Firefox remains flag-gated/unsupported. (4) CONFIRMED — getUserMedia works in installed (standalone/home-screen) web apps since iOS 13.4 (Mar 2020), per WebKit bug 185448 (broken from iOS 11.3-13.3). (5) HALF-OUTDATED — Android Chrome supports torch/zoom (since Chrome 59 via applyConstraints) and focusMode/focusDistance; on iOS, zoom shipped in Safari 17.0 (Sep 18 2023, exposed in MediaTrackCapabilities and constrainable), whiteBalanceMode in Safari 17.4 (Mar 5 2024), and torch was implemented Oct 2023 and confirmed working by iOS 17.5.1 (getSettings staleness fixed in Safari 18.4); only manual focus (focusMode/focusDistance) remains unsupported on iOS Safari as of Safari 26.x. The dossier should not claim iOS lacks torch/zoom or takePhoto on current iOS versions — only on pre-17.x/18.4 fleets.

## Reasoning

Each sub-claim checked against primary sources. (1) MDN Media Capture Constraints guide states verbatim: "most constraints aren't requirements; instead, they're requests... The user agent will try to provide what you request but will not guarantee that what you get will match", and only exact/min/max are mandatory — confirming loose honoring; e.g. asking 1920x1080 may yield 1920x900. (2) MDN's canonical "Taking still photos" pattern sizes the canvas from video.videoWidth/videoHeight (height = video.videoHeight/(video.videoWidth/width)) before drawImage(video,0,0,w,h), explicitly to preserve the stream's aspect; MDN object-fit defines fill (initial value) as "stretched to fit" on aspect mismatch and cover as "clipped to fit" — establishing that distortion is a presentation/capture-side scaling artifact, fixable entirely in JS/CSS. (3) W3C mediacapture-image (WD, Apr 23 2025) defines takePhoto as "the result of a single photographic exposure" vs grabFrame as a snapshot of the live video; Chrome's vendor blog says takePhoto "uses the highest available photographic camera resolution" and the API shipped in Chrome 59 on Android and desktop. The "iOS Safari no" half is refuted for current iOS: webkit.org's Safari 18.4 post (Mar 31 2025) states "WebKit for Safari 18.4 adds support for Image Capture API", MDN BCD (main, fetched 2026-06-10) records ImageCapture/takePhoto/getPhotoCapabilities/getPhotoSettings = Safari 18.4 and grabFrame = Safari 26, and STP 244 (2026) release notes show ongoing takePhoto fixes — I weighted vendor release notes + BCD over the conflicting, stale caniuse curated table ("Safari not supported", 77.07% global) and a low-quality third-party blog. (4) WebKit bug 185448 (filed May 2018) is RESOLVED FIXED with maintainer/reporter confirmations that getUserMedia works in home-screen standalone apps "as of iOS 13.4 beta 1" (Feb 2020), shipping Mar 2020 — confirming the iOS 13.4 claim exactly. (5) Chrome: torch/zoom adjustable live via applyConstraints since Chrome 59 (vendor blog). iOS: Apple's official Safari 17 release notes contain "Added support for exposing zoom in MediaTrackCapabilities (106498125)"; webkit.org Safari 17.4 post adds whiteBalanceMode; WebKit bug 243075 ("torch track constraint ignored on iOS") is RESOLVED with the WebKit engineer stating he added torch support (Oct 2023) and a field report of it working on iOS 17.5.1; Safari 18.4/STP 211 fixed getSettings returning stale torch/whiteBalanceMode values. No WebKit/Apple release note or BCD entry shows focusMode/focusDistance on Safari through 26.x, and practitioner docs (Dynamsoft) still document focus control as Chromium-only — so "focus not on iOS" stands while "torch/zoom not on iOS" is obsolete by ~2 years. Residual uncertainties (noted, not verdict-changing): Apple's zoom wording covers capabilities exposure (constraint settability is implied by the constrainable-property model and later WebKit fixes), and whether WebKit's takePhoto returns true full-sensor resolution on iPhone hardware (vs stream-sized exposures) is not independently benchmarked in any primary source I found.
