# PWA vs native reality for India field employees on a bill-capture app (2024-2026): installability, iOS constraints, offline patterns, low-end Android, camera quality, i18n, and the TWA/Capacitor escape hatches

## Executive Summary

For an India-first employee bill-capture product, the PWA path is viable and strategically correct, because the install base is overwhelmingly Android (93.2% vs 6.7% iOS in India, May 2026, StatCounter) and Android PWAs are near-native: Chrome mints a real WebAPK (app drawer, settings, URL intent capture), the service-worker requirement for install was dropped in Chrome 108, web push works, and an installed PWA can register as a Web Share Target to receive bill photos shared from WhatsApp or the gallery (Chrome 76+, Android-only). The genuinely load-bearing engineering decision is the camera: getUserMedia delivers only video-stream resolution frames, ImageCapture.takePhoto() (full still resolution) is Chromium 59+ and only reached Safari in 18.4 (March 2025), and a long-lived WebKit bug (252465) still intermittently blacks out getUserMedia streams in iOS standalone PWAs through iOS 18.4.1 — so the primary capture path must be <input type=file capture="environment"> invoking the native camera app at full sensor resolution, with live-preview edge detection as progressive enhancement only. iOS is the risk concentration but a small one for this ICP: no install prompt (share-sheet A2HS only), push only for installed Home Screen apps since iOS 16.4, no Background Sync, no share target, storage isolated between Safari and the installed app (forcing re-login), and Apple demonstrated platform risk by briefly killing EU Home Screen web apps in iOS 17.4 beta before reversing on March 1, 2024 (rest-of-world, including India, was never affected). Offline-first is mandatory and well-patterned: an IndexedDB outbox with Workbox background-sync replay (with SW-startup fallback for Safari), navigator.storage.persist(), and generous quotas (Chrome 60% of disk per origin; Safari 17 gives Home Screen web apps the same quota as the browser, and installed apps are exempt from the 7-day script-writable-storage purge). Data cost is no longer the binding constraint in India (~$0.09/GB, 27.5→31GB/month average usage) — network consistency is (even Jio's best-in-class Consistent Quality score is only 66.5%, i.e. roughly a third of demanding tests like image upload fail thresholds), which argues for client-side compression and queued upload UX, not data austerity theatrics. Low-end Android (4-8GB RAM is the largest segment at ~42%) imposes real budgets: ~150KiB HTML/CSS + 300-350KiB JS gzipped for a 5-second P75 first load, iOS canvas caps (16.78M pixels per canvas, ~384MB total canvas memory) and ~300MB practical WASM allocation ceilings mean heavy document-scanner processing should default to the server with on-device WASM as an opt-in for capable devices. Vernacular UI is non-negotiable for field staff (98% of India's 886M internet users consume Indic-language content; 55% of users are rural), and the web stack ships language updates instantly without store review. The staged recommendation: (1) responsive web with file-input capture works for 100% of devices including iOS Safari day one; (2) installable PWA adds the Android-native experience (WebAPK, push, share target, offline outbox) for ~93% of Indian users; (3) wrap the same PWA as a TWA via Bubblewrap when customers demand Play Store presence (mind the July 2024 spam/minimum-functionality policy — TWAs of your own quality PWA are officially supported, thin webviews are removed); (4) only reach for Capacitor if iOS push reliability or native camera UX becomes a paid-deal blocker, since it buys APNs push without the Home-Screen-install precondition and a native camera plugin at the cost of app-store review overhead. Indian precedent (Flipkart Lite's 70% conversion lift from home-screen users; Ola's 200KB PWA growing tier-2/3 traffic 68%) proves the model for exactly this user class, even though those canonical numbers are 2016-17 vendor-marketing era; notably, no leading Indian field-force or expense vendor leads with a PWA today, which is both a gap and a caution.

## UX Patterns

- Primary capture via native camera handoff: a big 'Snap bill' button backed by <input type=file accept="image/jpeg,image/png" capture="environment"> — used by web.dev guidance and Dynamsoft-style scanner vendors as the fallback — because it gets the full-resolution native camera app on 100% of devices with zero permission prompts; getUserMedia live preview with edge-detection overlay is layered on only where supported (Chromium; iOS only in-browser, not standalone, due to bug 252465). Works because it converts the platform's weakest API surface into its strongest (the OS camera app).
- Fallback ladder for scanner-grade output: ImageCapture.takePhoto() (full still res, Chromium 59+/Safari 18.4+) -> getUserMedia frame to canvas (stream res, downscaled to <16.7M px for iOS canvas limits) -> file-input capture (always). Feature-detect at runtime; never hard-require getUserMedia. This is the concrete iOS mitigation the dossier conclusion needs.
- Outbox/queue pattern for flaky networks (used by MapmyIndia WorkMate natively; Workbox pattern on web): compress client-side (~1-2MP JPEG for OCR upload, keep original optionally), write submission + blob to IndexedDB immediately, mark UI 'saved on phone', replay via Background Sync on Chromium and on app-open for Safari; explicit queued/syncing/synced/failed chips per bill so field staff trust the app on dead networks.
- Deferred install prompt on Android: capture beforeinstallprompt, suppress it, and trigger after the first successful submission ('Add Kharcha to your phone to submit bills in 2 taps'), with manifest description + screenshots to get Chrome's rich bottom-sheet dialog instead of the mini-infobar. Flipkart Lite's 60%-of-visits-from-icon and 70% conversion lift is the canonical justification for investing in this funnel.
- iOS install coaching instead of prompt: detect iOS + display-mode:browser and show a dismissible share-sheet walkthrough ('Tap Share -> Add to Home Screen'), because beforeinstallprompt does not exist on iOS; expect low uptake and never gate features behind install on iOS.
- Share-target ingestion (Android only): register share_target in the manifest so employees can forward a WhatsApp bill photo or gallery image straight into the submission flow (multipart POST). On iOS, the equivalent is 'upload from photo library' inside the app — design copy must not promise share-to-app on iPhone.
- Session continuity across iOS install boundary: because Safari and the installed PWA share no cookies/localStorage (only SW registration + CacheStorage), pass a one-time token via CacheStorage or send a magic link/OTP on first standalone launch — otherwise every iOS installer hits a surprise login wall (Netguru-documented pattern).
- Notification strategy split: web push for approval nudges and 'credits exhausted, ask admin' nudges on Android PWA; on iOS rely on WhatsApp/email/SMS instead of push (push requires Home Screen install + user-gesture opt-in since 16.4, and the install rate will be low) — this aligns with the product's WhatsApp-first thesis.
- Storage hygiene on first run: call navigator.storage.persist() (heuristically granted to Home Screen web apps per WebKit), show 'bills saved on phone' storage indicator, and upload-then-prune blobs; warns against relying on uninstalled Safari sessions where the 7-day script-writable storage purge applies.
- Low-end budget discipline: ship the submission flow under ~350KiB gzipped JS (Alex Russell P75 budget), test on a Galaxy A24-class device, lazy-load the WASM document-scanner module only when navigator.deviceMemory >= 4 and fall back to server-side perspective correction otherwise (Scanbot itself exposes low-power toggles).
- Vernacular-first field UX: language picker on first launch persisted per device, Indic-script UI strings, icon-heavy navigation and numeric-keypad-first forms for low-literacy field staff (98% of Indian users consume Indic-language content; 55% rural); web stack lets ops fix translations same-day with no store review.
- TWA packaging pattern when IT admins demand 'a real app': Bubblewrap-wrap the production PWA, serve assetlinks.json, ensure offline-200 and 404/5xx handling per Chrome 86 TWA quality criteria, and differentiate the listing with genuine capabilities (offline outbox, share target, shortcuts) to stay clear of Play's July 2024 webview-spam enforcement.

## Risks / Caveats

- iOS standalone camera instability is unresolved platform risk: WebKit 252465 reproduces through iOS 18.4.1 (June 2025) with no reliable workaround; any design that makes getUserMedia the primary capture path on installed iOS PWAs will generate field failures. Mitigation (file-input capture) is mandatory, not optional.
- Apple platform risk is demonstrated, not hypothetical: the Feb 2024 EU Home Screen web-app removal (reversed Mar 1, 2024) shows Apple will degrade PWAs when strategically convenient; India was unaffected, but a product with material iOS exposure should keep the Capacitor option warm.
- No Background Sync on iOS/Safari means queued bills only upload when the employee reopens the app — pair the outbox with WhatsApp/SMS reminders, and set reviewer SLAs assuming up to a day of sync lag for iOS-or-closed-app cases.
- Storage is durable only after install or persist(): bills queued in an uninstalled Safari session are exposed to the 7-day script-writable storage purge and LRU eviction under disk pressure on cheap phones with full storage — upload promptly and treat IndexedDB as a buffer, not a store of record.
- The canonical India PWA numbers (Flipkart 70% conversion lift, Ola 200KB/68% tier-2/3 growth) are 2016-17 Google/vendor marketing figures from a 2G-era web; directionally right for this user class but should not be quoted as current benchmarks. No leading Indian expense/field-force vendor ships PWA-first today — the strategy is differentiated, not market-validated (medium confidence).
- Play Store TWA carries policy tail-risk: Play removes 'webview spam' and the July 17, 2024 minimum-functionality update raised the bar; TWAs of your own quality PWA are officially supported (Google codelab) but community rejection/suspension threads exist — keep evidence of app-like functionality for appeals.
- caniuse version labels for mobile browsers reflect only the current release (e.g. 'Chrome for Android 148'), so per-version mobile support history is approximate; Android Chrome had Background Sync from ~v49 per the desktop column.
- Quantitative quotas differ by source vintage: web.dev cites Firefox 2GB/eTLD+1 and Safari ~1GB-with-prompts, while Safari 17's policy moved to 60%-of-disk origin quotas — cite the WebKit 14403 post for current iOS behavior.
- Several India market figures are analyst/vendor-mediated (IMARC RAM mix 42.3%, $0.09/GB cable.co.uk 2023 vintage, IAMAI via press coverage); ranges may have shifted post-2024 tariff hikes (Jul 2024 telecom price increases ~11-25% are widely reported but were not directly verified here — treat as medium confidence).
- Claims about incumbent expense apps (Zoho Expense/Happay/Fyle being native-first) rest on vendor positioning and training knowledge, not a systematic audit — verify against current Play/App Store listings before printing in the dossier.

## Recommendations

- Stage 0 (MVP, weeks 1-8): responsive mobile web with file-input capture=environment as the only camera path, server-side perspective correction + OCR, OTP/magic-link auth. This works identically in iOS Safari, Android Chrome, and inside WhatsApp's in-app browser, requires zero install, and sidesteps every getUserMedia/WASM/canvas constraint. Do not block submission on JS-heavy scanning; keep first load within ~150KiB markup/CSS + ~300KiB JS gz (P75 budget).
- Stage 1 (default GA posture): installable PWA for Android — manifest with 192/512 icons + screenshots + description (rich install sheet), Workbox SW with offline outbox + BackgroundSyncPlugin, beforeinstallprompt deferred to post-first-submission, share_target for WhatsApp/gallery forwards, web push for approval and credit-exhausted nudges, navigator.storage.persist(). Treat iOS as 'works in Safari, install optional': coach A2HS, never gate on install, route notifications via WhatsApp/email.
- Stage 2 (pull-based, ~1-2 weeks effort): TWA via Bubblewrap into Play Store when a customer's IT or trust objections demand store presence ($25 one-time fee, same codebase). Pre-empt Play policy risk: pass TWA quality criteria (asset-links, offline 200, error handling), keep the listing capability-rich, and expect occasional human-review friction under the July 2024 spam/minimum-functionality policy.
- Stage 3 (only on demonstrated revenue blockage): Capacitor wrapper — first for iOS if (a) iOS field-employee share grows materially beyond ~7%, (b) buyers require push on iPhones without install coaching, or (c) the standalone-camera instability (WebKit 252465) generates support load. It buys native camera UI with full-res + crop, APNs push, and App Store presence; budget for app review, privacy strings, and a release pipeline. Keep the web app canonical and the wrapper thin.
- Camera engineering rule: implement the capture fallback ladder (ImageCapture.takePhoto -> getUserMedia+canvas -> file-input) behind one component; on iOS standalone default straight to file-input. Downscale to <=12MP before any canvas work (iOS 16.7M-pixel canvas cap), compress to ~1-2MP JPEG for OCR upload, and force accept="image/jpeg,image/png" to dodge Safari 17 HEIC conversion traps; normalize HEIC server-side anyway for WhatsApp-channel images.
- Keep intelligent processing server-side by default (aligns with the submissions-metered pricing: the meter pays for server OCR). Offer on-device WASM edge-detection only as progressive enhancement on >=4GB-RAM devices — the ~300MB practical WASM ceiling and OpenCV.js leak footguns make it a reliability tax on 2-4GB phones.
- Design the soft paywall around the offline outbox: when credits exhaust, keep accepting and queueing uploads (IndexedDB + server inbox), pause OCR, and surface the employee-side 'nudge admin' CTA via Android push/WhatsApp template — the same queue infrastructure serves both flaky networks and the paywall, one codepath.
- Localize from day one: ship Hindi + 2-3 state languages for launch ICPs, icon-first flows; treat instant web deployment of language packs as a sales point against native incumbents whose translation fixes ride 1-2 week store-release trains.
